Own GPUs at small volume (Q10.7). A small volume does not justify an own GPU cluster by cost. Only control needs justify it. There are five such needs. Data must not leave the organization. 10.2Model gateway contracts

Answers: Q10.9, Q10.10, Q10.11, Q10.12, Q10.13, Q10.14, Q10.15, Q10.16, Q10.17, Q10.18, Q10.19, Q10.20, Q10.21, Q10.22, Q10.23

The agent never talks to a model server. It talks to the inference gateway. The gateway is the only path to a model (Artifact 6, Q6.12). It gives one interface for all models. A change of model is a configuration change (Artifact 2, 2.5).

Figure 1. Component diagram of the inference gateway. The agent sees one contract. The adapters hide the model server. Dashed parts are off by default.

Who owns what (Q10.9)

OwnerResponsibilities
Inference serviceRun the model. Serve requests. Report token usage.
Application (gateway)Build requests in our format. Version prompts. Choose model and parameters. Parse and validate responses. Validate and run tools. Retry, time out, and escalate. Account for tokens. Log provenance. Check the output quality.

Server differences stop at the adapter. So the agent sees the same behavior for every model. Model output is untrusted data (Artifact 6, trust zones). The gateway validates it before the platform uses it.

Adapter rules (Q10.10, Q10.11, Q10.12)

  • The gateway has two thin adapters, on the official OpenAI and Anthropic SDKs (Artifact 6, Q6.28). Each implements the contract. The OpenAI-compatible adapter also serves the self-hosted engine.
  • All server-specific code stays in the adapter. This includes client calls, authentication, formats, error types, and model IDs.
  • The agent must not import server-specific code.
  • The adapter converts every response to the internal structure. A tool call has an id, a tool name, and parsed arguments.
  • The adapter flags malformed output. It must not pass it on silently.
  • The gateway keeps the raw response, or a reference to it, for debugging.
  • Only redacted content reaches a model (Artifact 5, SC-09). If the redactor fails, the evidence counts as missing. Nothing goes out raw.
  • Contract tests check that every adapter behaves the same way.

Tool proposals (Q10.16)

A tool call from the model is a proposal. It is not an action. The ToolProposal holds: proposal id, request id, tool name, arguments, status, and the validation result with a reason. The status is proposed, valid, rejected, or executed.

Validator checkRule
ToolThe tool must exist and must be allowed for this task.
ArgumentsThe arguments must match the tool schema.
Permissions and limitsThey must hold. Every write also needs checks and human approval, outside the agent (Artifact 2, 2.3).
ResultOnly valid proposals reach the executor. The gateway logs rejected proposals. It may return them to the model.

Open: the tool list and the schemas come from Artifact 9.

Result status and handling (Q10.17 to Q10.21)

StatusMeaningHandling
completedThe model finished.Parse and validate. Only this status is a finished answer.
length_limitThe model hit the token limit.The result is incomplete. Do not use it as final. Retry with a larger limit or a smaller task, within budget.
interruptedThe stream ended without a completion signal.Keep the partial text in the log. Flag it. Do not use it as final. Record the usage.

errorThe call failed.Apply the retry rules (10.7).

The adapter maps the stop reasons of the model server to these statuses. Validation runs in this order: normalize, parse JSON, check the schema. The gateway never passes invalid output to a tool or to the next step. It logs every refusal and every failure with provenance.

Figure 2. Flowchart of result handling. The adapter maps server stop reasons to one status. Only a completed result that passes the schema check is final.

Capability incompatibility (Q10.22)

The gateway keeps the capability matrix (10.1). Before it sends a request, it checks the capabilities that the task needs. If a model lacks one, the gateway follows these rules in order.

  1. Route the request to a model that has the capability.
  2. Emulate the capability only where the configuration allows it. For example, ask for JSON in the prompt, then apply the schema check.
  3. Otherwise reject the combination with a clear error.

Emulation is explicit configuration. It is never silent. Open: which skills need which capability comes from Artifact 9.

No automatic fallback (Q10.39)

Artifact 2 decides this (2.5). The platform has no CPU fallback and no automatic cloud fallback. If the main model or the reviewer model is down, the platform halts. It escalates to a person with the alert and the evidence so far. Escalation is plain system logic. It needs no model. A slow model service escalates after the timeout (Artifact 4, NFR-12).

An automatic fallback has these risks:

  • A different model behaves differently. Prompts for one model may fail on another.
  • The other model may lack a required capability.
  • Data would go to another provider. The organization has not approved it.
  • Costs differ.
  • All requests arrive at once and overload the second server.
  • Tracing gets harder.

High availability reduces the need for a fallback.

10.9BM25 ingestion and search

Answers: Q10.40, Q10.41, Q10.42, Q10.45, Q10.46, Q10.47, Q10.48, Q10.49, Q10.50, Q10.52, Q10.53, Q10.54, Q10.55, Q10.56

The model has no knowledge of our systems. Retrieval fixes this. At question time, the knowledge retriever searches runbooks and past incidents (Artifact 6, Q6.13). It puts the best passages in the prompt. The model then answers from them. Ingestion is the earlier preparation step.

Figure 5. Flowchart of ingestion and search. Search reads one fixed index revision. The scope and access filter runs before the model sees any text.

Ingestion (Q10.42)

  1. Collect the documents from the agreed sources: runbooks and past incidents.
  2. Read and clean the text. Keep the headings and code blocks.
  3. Split the text into chunks by heading (10.10).
  4. Add metadata to each chunk: source, document id, version, heading path, date, service, access information.
  5. Build the BM25 index as a new index revision. The previous revision stays usable.
  6. Check the result with counts and sample searches.
  7. Run again when documents change. Remove deleted documents.

Past incidents come from the incident store. It holds only redacted evidence (Artifact 5, SC-09). V1 uses synthetic runbooks, because Artifact 2 allows only synthetic fixtures. The documents are text with headings (L10-A6). Open: Artifact 2 does not list the runbook set.

ItemRuleLabel

Why BM25 first, and embeddings later (Q10.47 to Q10.50)

TopicPosition
Why BM25 firstExact identifiers are the main need. BM25 finds them reliably. It needs no embedding model and no vector index. It runs in the program. The same input gives the same output.
What embeddings addEmbeddings turn text into vectors by meaning. A question with different words can then find a similar document. A weakness: similar identifiers can blur.
Hybrid mergeRun BM25 and vector search. Merge the ranked lists with Reciprocal Rank Fusion. A document gets about 1 / (60 + rank) from each list. The scores add up. The merge uses ranks because the two scores have different scales.
When to addArtifact 2 plans an embedding model on CPU. The team adds it when evaluation (10.13) shows that wording differences cause misses. Artifact 6 names the same trigger (ADR-09).

Assumption L10-A7: BM25 alone misses few documents because of wording in V1.
