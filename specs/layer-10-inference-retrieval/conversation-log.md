## What A2 settled for Layer 10

- **Data rule:** incident data must not leave the organization (Q2.12). So no external model API.
- **Hosting:** self-hosted open-weight models on the organization's existing GPUs, with high availability. One main model and one different reviewer model. No new infrastructure spend (Q2.12, Q2.15, Q2.19).
- **No custom model** in V1 (Q2.11). **No CPU fallback and no outside provider.** If the main or reviewer model is unavailable, the platform halts and escalates to a person (Q2.19).
- **Model interface:** all model access goes through one interface, so a change of model is a configuration change (A2 section 2.5).
- **Concurrency:** 3 incidents at the start, configurable. Extra incidents wait in a queue, ordered by severity and then by age (Q2.17).
- **Budget per incident:** set by experiment on the synthetic fixtures: measured model calls, tokens and GPU time, plus a buffer. A provisional hard cap applies during the experiments (Q2.16). Cost is measured as GPU time because the hardware is fixed.
- **Time:** a full investigation may run 15 to 20 minutes, without human approval waits, sandbox tests and applying a fix. A shorter phase 1 limit, provisionally 5 minutes. The fix-phase limit is not set (Q2.18).
- **Open items A2 gives to Layer 10:** which open-weight models (main and reviewer) and the GPU sizing; the high-availability design of the model servers; the buffer, provisional cap and time limits, together with Dhanush; assumptions L2-A8 and L2-A10.

### Decisions A

- **Q10.1 Model that generates tokens:** A transformer-based, decoder-only, autoregressive LLM generates the tokens. It computes a probability for the next token, selects one, appends it to the input and repeats until a stop token or the max_tokens limit. A2 limits the choice to self-hosted open-weight models. The exact models (one main model and one different reviewer model) are chosen in Layer 10 (see 10A-3).
- **Q10.2 Model vs provider:** Treat the model (family, version, model ID) and the provider (who hosts and serves it, and its interface) as two separate things. The platform records both as separate fields, with the exact pinned model version, on every request and result. The same model can be served by different providers, and the same provider offers many models. The application uses its own internal model name that maps to the provider's model ID. Under A2 the provider is our own inference service that serves the open-weight model; model and provider are still recorded as separate fields.
- **Q10.3 Delivery approach without GPU operations:** Settled by A2 (Q2.12, Q2.15, Q2.19). The models run self-hosted on the organization's existing GPUs, with high availability. This is what the first draft of this answer called the fallback; it is now the main choice. A hosted API is not allowed because incident data must not leave the organization, and a CPU-only fallback is not allowed (A2 Q2.19). The condition "no GPU operations" therefore cannot be met: the team operates the serving software on its own GPUs. Existing hardware means no new GPU spend (A2 Q2.15). The first draft, written before A2 existed, chose managed (hosted) inference as the primary option; this answer replaces it.
- **Q10.4 Self-hosted inference vs external provider:** With self-hosted inference, the organization runs the GPUs, the serving software, scaling, uptime and security patches itself. In return it gets full control: data stays inside its own network (data residency), it chooses and pins the exact model version, and it is not bound by a provider's rate limits or deprecation schedule. Costs are fixed and GPU-based, so self-hosting pays off only at high, steady volume; at low or uneven volume the GPUs sit idle and cost more. Only open-weight models can be self-hosted, so closed models such as Claude cannot be used, and quality may be lower. Small models for narrow tasks are easier and cheaper to self-host. With an external provider, the provider handles GPUs, scaling and uptime. We pay per token and start fast, but data leaves our network and we depend on the provider's limits, pricing and outages. A2 chose self-hosted inference because of the data rule, on hardware the organization already has. Cost is therefore not the deciding reason, and the high-and-steady-volume point is background only (10A-9).
- **Q10.5 Evaluating Claude and Tinker:** Claude and Tinker are two different kinds of service, not substitutes for the same job. Claude is an inference service: we send a prompt, the provider runs its closed model on its own GPUs and returns tokens, and we pay per token. Tinker is a training service: we write the training loop locally on a CPU machine, Tinker runs the heavy training on its GPU clusters, and it fine-tunes open-weight models (using LoRA). It also offers sampling, and trained weights can be downloaded and used elsewhere. They should be compared on the same criteria: the job each one does, who runs what, what data leaves our network, cost, limits and lock-in, which models are available, and output quality on the same test set. Result under A2: neither is used in V1. Claude is an external model API, and A2 forbids external model APIs because incident data must not leave the organization (Q2.12). Tinker is an external service for building custom models, and A2 says there is no custom or fine-tuned model in V1 (Q2.11). A2 does not mention Claude or Tinker by name; the exclusion follows from these two rules. A2 says to revisit the custom model when enough learned incidents exist; this comparison method can then be used again. Tinker's current features and model list must be checked in its official docs before any later use.
- **Q10.6 Responsibilities transferred with managed inference:** Under managed inference the provider would take over the running of the serving infrastructure: provisioning servers and GPUs, deploying and updating the model, serving software and its patches, capacity planning and autoscaling, hardware failures, speed optimizations such as batching and caching, monitoring, and keeping the service up under its SLA (service level agreement, the provider's written promise about availability). A2 does not use managed inference, so in V1 these responsibilities stay with the team: provisioning on the existing GPUs, deploying and updating the models, serving software and its patches, capacity planning, high availability (A2 requires more than one copy of each model server; this design is a Layer 10 task, owner Irfan), hardware failures, speed optimizations, monitoring and uptime. The team also owns how its application uses the service, such as the choice of model and checking the outputs.
- **Q10.7 Own GPU cluster at small volume:** Settled by A2: V1 runs on the organization's existing GPUs (Q2.15), starting with 3 concurrent incidents (Q2.17). The justifying requirement is control reason (1) below, the data rule. The method below stays as the way to judge such a proposal. At small and steady volume, running our own GPU cluster is not justified by cost. The GPUs sit mostly idle and still cost money, and the team needs people to run them. A managed provider is cheaper and simpler. The decision can be justified only by control requirements, not cost: (1) data may not leave our network because of law or company rules (data residency); (2) a custom or fine-tuned model that no managed provider hosts; (3) strict control of model versions, with no dependence on a provider changing or retiring a model; (4) special latency or network needs, such as running offline or in a closed network; (5) a firm plan for volume to become large and steady soon, so that fixed GPU cost pays off. Even when justified, start smaller than a full cluster: rent one GPU server, or host the custom model with a provider, and grow only when volume requires it.
- **Q10.8 Serving infrastructure for GPU memory and batching optimizations:** A dedicated LLM serving engine is needed, not a plain model script. vLLM is the main candidate: it manages KV cache memory in small pages (PagedAttention) so less GPU memory is wasted, uses continuous batching (a finished request is replaced at once by a new one, so the GPU stays busy), supports prefix caching, and offers an OpenAI-compatible API server. Other candidates are SGLang (actively developed, reported to suit workloads with repeated prefixes), TensorRT-LLM (NVIDIA GPUs only, high speed goal, longer setup) and Hugging Face TGI (reported by secondary sources to be in maintenance mode, so verify before choosing it for new work). The KV cache itself saves computation time but uses GPU memory; it does not save memory. A2 requires self-hosting (Q10.3), so V1 needs a serving engine that can run two models (main and reviewer) on the existing GPUs for 3 concurrent incidents (L2-A10). The engine is chosen by benchmarking on our own traffic, not from published speed claims.
- **Q10.9 Provider vs application responsibilities:** The provider owns running the model: GPUs, serving, scaling, availability and model updates behind its API. The application owns everything that must behave the same whichever provider is used: building requests in our own format, prompts and prompt versions, model and parameter choice, parsing and validating responses, validating and executing tools, retries, timeouts and fallback, token and cost accounting, logging with provenance, data and security decisions, and checking output quality. Rule: provider differences stop at the adapter, so the agent sees one behavior. Under A2 the "provider" is our own inference service; the same boundary applies, and a change of model stays a configuration change.

### Decisions B

- **Q10.10 One internal model interface:** The application defines one interface: a ModelRequest goes in and a ModelResult comes out. One adapter per provider implements it by converting our request into that provider's format, calling the provider, and converting the response back. The agent talks only to the interface and never to a provider.
- **Q10.11 Isolating provider-specific communication:** All provider-specific code (SDK calls, authentication, request and response formats, error types, provider model IDs) stays inside the adapter. The agent never imports provider code. A configuration maps our internal model name to a provider and its model ID. Switching an existing provider is a configuration change. A new provider needs one new adapter, and the agent stays unchanged. Contract tests check that every adapter behaves the same way. This matches A2: all model access goes through one model interface, so a change of model is a configuration change.
- **Q10.12 Normalizing response formats:** Every adapter converts provider output into the same internal structure. A tool call becomes: call id, tool name, and arguments as a parsed object (the adapter parses JSON text). Malformed output is flagged in the adapter and not passed on silently. The raw provider response (or a reference to it) is kept for debugging.
- **Q10.13 ModelRequest fields (mechanism):** request id; incident id and task type; internal model name; instructions and messages (context); available tools (name, description, schema); parameters (max output tokens, temperature, stop sequences); required output format or schema; capability needs (tool calling, structured output); timeout and token budget; prompt version. TBD: the exact task types and per-task values come from A9.
- **Q10.14 ModelResult fields:** request id; content blocks (see Q10.15); stop reason; token usage (input, output, and cached tokens if reported); provenance (provider, provider model ID, internal name, pinned version); start time, end time and latency; retry count; error information if any; reference to the raw response. All of it is written to logs so any issue can be traced back.
- **Q10.15 Representing mixed content:** A response is an ordered list of typed blocks: text, tool proposal, and structured content (parsed JSON plus whether it matched the schema). Other types the provider returns, such as a refusal, also get their own type. Order is preserved. The application reads blocks by type and never depends on a provider's own layout.
- **Q10.16 Representing tool proposals (mechanism):** A tool call from the model is a proposal, not an action. A ToolProposal holds: proposal id, request id, tool name, arguments, status (proposed, valid, rejected, executed) and the validation result with a reason. A validator checks that the tool exists and is allowed for this task, that arguments match the tool's schema, and that permissions and limits are respected. Only valid proposals reach the executor. Rejected ones are logged and can be returned to the model. TBD: the tool list and schemas come from A9.
- **Q10.17 Provider refusal:** A refusal is a normal outcome, not a transport error. The adapter maps the provider's refusal signal to our own result status "refused" and carries the provider's message. The gateway does not retry the same request blindly and does not silently switch providers. The workflow or agent decides what happens next, for example rewording the request or escalating to a person. Every refusal is logged with provenance.
- **Q10.18 Token limit vs completion:** Each adapter maps the provider's stop reasons to a small set of our own: completed, length_limit, tool_request, refused, error. Only "completed" is a finished answer. "length_limit" marks the result incomplete and it is not used as final. The caller may retry with a larger output limit or a shorter input, within budget.
- **Q10.19 Disconnected stream:** A streamed response is complete only when it ends with the provider's explicit completion signal and a stop reason. A dropped connection, or a stream that ends without that signal, gives the status "interrupted". Partial text is kept for logs, flagged, and not used as final. Tokens may already be billed, so usage is still recorded. Retry follows the retry policy.
- **Q10.20 Truncated JSON:** Truncated JSON is an incomplete result and is not repaired by guessing. Check the stop reason first: if it is length_limit, retry with a larger output limit or a smaller task. Otherwise retry within the retry limit. After the limits, fail with a clear error. The raw output is logged.
- **Q10.21 Schema violations:** Validation runs in order: normalize the provider response, parse the JSON, then validate against the expected schema (required fields, types, allowed values). Invalid output is never passed to tools or to the next step. On failure, retry a bounded number of times, optionally sending the validation error back to the model. After the limit, fail with an error and log the raw output and the error.
- **Q10.22 Capability incompatibility:** The gateway keeps a capability matrix per model (structured output, tool calling, and so on). Before sending a request it checks the capabilities the task requires. If a model lacks one, the gateway routes to a model that has it. Where explicitly allowed for that skill, it emulates the capability, for example by asking for JSON in the prompt and applying the Q10.21 validation. Otherwise it rejects the combination with a clear error. Emulation is explicit configuration, never silent. TBD: which skills need which capability comes from A9.
- **Q10.23 Reproducibility:** Preserve for every result and investigation: internal model name, provider, provider model ID, the exact pinned version or checkpoint (never an alias such as "latest"), the model identifier the provider returned in its response, request parameters (temperature, max tokens and so on), prompt version, skill version, tool definition version, and request date and time. If a provider retires a version, exact re-running may be impossible. Then the stored inputs and outputs are the record.
- **Q10.24 Provider comparison:** Under A2 the comparison is between candidate open-weight models and serving engines, not between hosted providers. A2 sets these hard constraints: incident data must not leave the organization; models are open-weight and run on the existing GPUs with enough capacity for 3 concurrent incidents with two models (L2-A10); high availability; no CPU fallback; the self-hosted models must be good enough for multi-step tool use (L2-A8); the main and reviewer models are different. Compare candidates on: model quality for our tasks (from evaluation results), capabilities (tool calling, structured output, streaming, context window, maximum output, caching), GPU memory and GPU time needed, latency, version pinning (we hold the weights), license terms, and data handling (everything stays inside our network). Results go into the capability matrix. Open: which models and what GPU sizing (A2 assigns this to Layer 10, owner Irfan; see 10A-3).

### Decisions C

- **Q10.25 Unit of consumption:** The platform measures consumption in tokens, always as two separate numbers: input tokens and output tokens. Each model has its own tokenizer, so the same text gives different counts. Under A2 the hardware is fixed and there is no per-token bill, so the platform also measures model calls and GPU time per incident (A2 Q2.16). Counts come from the usage report of our model server, and estimates use the tokenizer of the specific model, not a tokenizer of our own design.
- **Q10.26 Distinguishing usage:** Every result records input tokens, output tokens, and cached tokens if the server reports them, never one combined total. They load the GPU differently: input is processed in parallel before the first token, and output is generated one token at a time. There is no price table because the hardware is fixed. Cost per request is expressed as tokens and GPU time, measured on the synthetic fixtures.
- **Q10.27 Estimating and controlling spend (mechanism):** Every call has a maximum output limit. Before a call, the worst-case usage is estimated from the counted input and that limit. Each incident has a total budget that covers all its calls, and calls stop when it is used up. A2 (Q2.16) sets how the budget is found: run the synthetic fixtures, measure model calls, tokens and GPU time, and set the cap at the measured baseline plus a buffer. During these experiments a provisional hard cap stops a runaway loop from taking the GPUs. A table of measured usage per task type gives an expected range, and an alert is raised when a call or incident goes outside it. TBD: the buffer size and the provisional cap come from the experiments (owners: Irfan, Dhanush).
- **Q10.28 Per-incident budget (mechanism):** Each incident has one total cap, measured in model calls, tokens and GPU time. A2 sets the value by experiment: the measured baseline plus a buffer (Q2.16). A budget ledger per incident holds the limit, the amount spent, and the amount reserved. Every call draws from it through a reservation (Q10.29). When the remaining budget cannot cover the next call, the call is refused, and the investigation ends with the best result so far or escalates to a person. A per-call output limit is a separate, smaller guard. A separate emergency reserve pool exists outside the incident budgets and is used only in emergencies. Which cases qualify, and who approves, is decided together with the stakeholders. TBD: the buffer and the provisional cap come from the experiments (owners: Irfan, Dhanush).
- **Q10.29 Cost reservations:** Before a call starts, estimate its worst-case cost (counted input tokens plus the maximum output tokens, and the expected GPU time) and reserve that amount from the incident budget in one atomic step. If the budget cannot cover it, the call waits or is refused and does not start. When the call finishes, replace the reservation with the real usage and release the unused remainder. Because the reservation happens before the call and cannot be taken twice, several parallel calls cannot together exceed the budget.
- **Q10.35 Missing usage report:** Never record zero usage. Record an estimate, flagged "estimated": input tokens counted by us, output tokens counted from the text received, or the maximum output limit if the response was lost. The estimate stays charged to the budget. The platform keeps its own usage log and regularly reconciles it with the model server's own logs and GPU metrics. Differences correct the ledger and improve the estimates.
- **Q10.36 Why not release the reservation at once:** The tokens are already consumed (GPU time is spent), but their amount is unknown. Releasing the reservation would show that budget as free while it is actually spent. New requests could then use it, and the total spending would go over the cap. So the reservation is kept (at the worst case) until the real usage is known, or until an estimate replaces it, flagged as uncertain.
- **Q10.30 Controlling concurrent inference requests:** One central limiter in the gateway allows at most N requests in flight per model server, with N set by the GPU capacity. A2 starts with 3 concurrent incidents, and the number is configurable (Q2.17). Extra incidents wait in a bounded queue, ordered by severity first and then by the oldest. When the queue is full, new work is delayed or rejected with a clear status (backpressure). Incidents wait; they do not fail because of load.
- **Q10.31 Per-incident concurrency (mechanism):** Each incident has its own maximum number of parallel calls, taken from the central limit. Scheduling is fair across incidents: an incident that asks for ten parallel operations cannot take the capacity of the others, and incidents take turns in the queue. TBD: the per-incident number comes from A9 (how much parallelism the agent design needs).
- **Q10.32 Enforcing a deadline (mechanism):** Each investigation gets an absolute deadline when it starts (start time plus allowed window). Before every new call, the remaining time is checked and the call never waits longer than that. When the deadline passes, new calls stop, running calls are cancelled, reserved budget is released, and the investigation ends with the best result so far or escalates to a person. A2 (Q2.18) gives the limits: a full investigation may run 15 to 20 minutes; human approval waits, sandbox tests and applying a fix are not counted; the first phase (propose the revert) has a shorter limit, provisionally 5 minutes. TBD: the fix-phase limit and the final values come from the experiments (owners: Irfan, Dhanush).
- **Q10.33 Two time limits (mechanism):** The request timeout (for example 30 seconds) protects against one hung call. The investigation deadline (A2: 15 to 20 minutes, with a provisional phase 1 limit of 5 minutes) is the hard limit for the whole investigation. The effective timeout of a call is the smaller of the request timeout and the time left before the deadline. A timed-out call does not end the investigation; it may be retried while time remains. When the deadline is reached, everything stops. TBD: the model-call timeout is set from the experiments (owners: Irfan, Dhanush).
- **Q10.37 Controlling retry amplification (mechanism):** Retries happen in one layer only, normally the gateway. Other layers report failures upward and do not retry model calls themselves. Without this, three layers with three attempts each can turn one request into 27. Attempts are capped (for example two or three), each retry waits longer than the last (exponential backoff with a little random delay), each retry is charged to the incident budget, and the deadline is respected. Only temporary errors are retried. TBD: which component owns retries is decided in A9.
- **Q10.38 No retry on permanent authentication errors:** A wrong or expired key fails the same way every time, so retrying only wastes time and cost, and repeated bad attempts can get the account blocked. The request fails fast, the provider is marked as misconfigured, and operators are alerted. This differs from temporary errors (too many requests, server errors, timeouts), which may be retried.
- **Q10.39 Automatic cross-provider fallback (mechanism):** Settled by A2 (Q2.19): there is no outside provider and no CPU fallback. If the main or the reviewer model is unavailable, the platform halts and escalates to a person with the alert and the evidence collected so far. Escalation is plain system logic and needs no model. The risks of an automatic fallback stay valid as the reasons: another model behaves differently and prompts written for one may fail on another; it may lack a required capability (Q10.22); data would go to another provider, which the data rule forbids; costs differ; all requests arriving at once can overload the second server; and tracking which model produced which result gets harder. High availability (more than one copy of each model server, A2) reduces the need for a fallback.
- **Q10.34 Cumulative token tracking (mechanism):** Every model call is tagged with the incident id and its role (agent, critic or revision). At the end of each call its usage (input, output and cached tokens) is added to the incident's ledger (Q10.28). The total is the sum of all calls, and it can be split by role. Before each loop round the remaining budget is checked (reservation, Q10.29), and the number of rounds is capped, otherwise a critic and revise cycle cannot be stopped from spending. Tokens used by retries go into the same ledger (Q10.37). TBD: the loop steps, their number and their limits come from A9.

### Decisions D

- **Q10.40 Runbooks during investigation (mechanism):** Runbooks are ingested into the same searchable index as other documents (Q10.42). The agent gets a retrieval tool it can call during an investigation with a query, for example an error code or service name. It receives the most relevant runbook sections with their source, version and section path. Runbooks are reference information for the agent, not commands: any action they suggest still goes through the normal tool validation (Q10.16). Incident priority or service name can be stored as metadata to filter results. A2 says V1 uses sanitized synthetic fixtures only and no real incident data, so the runbooks used in V1 are synthetic. TBD: which runbooks, and who writes them, is not stated in A2 (owner: A2 team).
- **Q10.41 Retrieval improving answers:** Without retrieval the model answers only from what it learned in training, which knows nothing about our systems and may be out of date, so it may guess. With retrieval, at the time a question is asked, the platform searches our documents, puts the most relevant passages into the prompt, and the model answers from them. This lets answers use our own current procedures, cite the source passage, and be checked more easily. Retrieval happens when a question is asked, not during ingestion. Ingestion is the earlier preparation step (Q10.42).
- **Q10.42 Ingestion process:** (1) Collect documents from the agreed sources. (2) Read and clean the text while keeping structure (headings, code blocks). (3) Split into chunks with heading-aware chunking (Q10.43, Q10.44). (4) Attach metadata to each chunk: source, document id, version, heading path, date. (5) Build the search index (BM25 first) as a new index revision, so the previous revision stays usable. (6) Check the result with counts and sample searches. (7) Re-run when documents change, including removing deleted ones. Index revisions, stale documents and deleted documents are covered in Q10.52 to Q10.55.
- **Q10.43 Dividing documents into retrievable units:** Split each document at its natural structure (sections and subsections), so every chunk covers one topic and can be understood alone. Chunks have a size limit; a section that is too long is split further at paragraph or step boundaries, with a small overlap. Very short neighbouring sections may be merged. Each chunk keeps a pointer to its document and position.
- **Q10.44 Heading-aware chunking:** Chunks are cut at headings, and the full heading path (for example "PostgreSQL > Failover > Step 3") is stored with every chunk, both in the indexed text and in the metadata. A fixed-size cut can separate "run promote" from the heading that says which system and situation it belongs to; heading-aware chunking prevents this. Code blocks and numbered steps are never cut in the middle.
- **Q10.45 Lexical retrieval for exact identifiers:** Use BM25, a lexical (exact word match) method. Engineers search for exact strings such as error codes, function names and configuration keys, and embedding-based search can blur such strings with similar ones. The tokenizer must keep identifiers such as ERR_4012 or max_connections whole (or index them both whole and split) so exact searches match.
- **Q10.46 Importance of rare terms:** BM25 weights each term by inverse document frequency (IDF): a term found in few documents gets a high weight, and a term found in almost all documents (such as "error") gets a low weight. So a rare error identifier that appears in only a few documents ranks those documents high. BM25 also limits the gain from repeating a term many times and adjusts for document length.
- **Q10.47 Vector embeddings:** Embeddings turn text into vectors by meaning, so a question and a document that use different words with similar meaning end up close together. The question is embedded and compared with the chunk vectors (cosine similarity), and the closest chunks are returned. This fixes vocabulary mismatch, for example "the database answers slowly" against "high query latency". Weaknesses: similar exact identifiers can blur, and it needs an embedding model and a vector index, which is extra infrastructure.
- **Q10.48 Search by conceptual similarity:** Semantic (vector) search: chunks are embedded at ingestion and stored in a vector index. At search time the query is embedded and the nearest chunks are returned.
- **Q10.49 Combining keyword and semantic results:** Hybrid retrieval: run BM25 and vector search separately, then merge the two ranked lists with Reciprocal Rank Fusion. Each document gets about 1 divided by (60 plus its rank) from each list, and the scores are added. Documents ranked high in both lists rise to the top. RRF uses ranks and not raw scores because BM25 scores and similarity scores are on different scales.
- **Q10.50 Why BM25 first:** Exact technical identifiers are the main need, and BM25 handles them reliably and explainably. It needs no embedding model, no vector database and no extra cost, runs inside the program, and gives the same output for the same input, so it is reproducible. Embeddings are added only if evaluation (Q10.51) shows that vocabulary mismatch causes missed documents.
- **Q10.51 Measuring retrieval quality:** Build a labeled set of real questions with known correct documents or chunks (ground truth). Measure Recall@10 (is the correct document in the top 10), Precision@10 (how many of the top 10 are relevant) and MRR (mean of 1 divided by the rank of the first correct result). Re-run the same set after every change to chunking or search method and compare. Keep the results together with the index revision.
- **Q10.52 Immutable index revisions:** Every ingestion run creates a new index revision with its own id, and a revision is never edited. It records the documents, their versions and content hashes, and the chunking and tokenizer settings. Each investigation records the revision it used, so it can be reproduced later. Old revisions are kept for the agreed retention period, or can be rebuilt from the stored document versions.
- **Q10.53 Preserving source version and text span:** Each citation stores the document id, the document version, the exact text span (start and end position) and a content hash of the cited text. If the document changes later, the cited text can still be shown from the stored version, and the hash proves it was not altered.
- **Q10.54 Detecting stale documentation:** No single test exists, so signals are combined: age beyond a review date kept in metadata; mentions of services or versions that no longer exist; a newer document that conflicts with it; and engineer feedback that a procedure failed. Suspected stale documents are flagged, ranked lower and sent to the document owner for review, and are not silently deleted. Automatic detection is imperfect, so owner review is required.
- **Q10.55 Deleted documents:** Each ingestion run checks which documents have disappeared from the source. The next index revision does not contain them (or marks them with a tombstone), so search no longer returns them. Older revisions stay unchanged, so earlier investigations can still be reproduced. Exception: if a document is removed for security or legal reasons, it is also removed from older revisions, with approval. Check: searching for text from a deleted document returns nothing.
- **Q10.56 Document-level permissions (mechanism):** Each chunk carries the access information of its source document (the groups or roles allowed to read it), stored at ingestion. At search time results are filtered by the requester's permissions before ranking and before anything reaches the model, so the model never sees text the engineer may not read. The agent searches with the identity of the engineer who asked. The default is deny. Citations, snippets and result counts must not leak restricted documents. Access information is refreshed when permissions change. A2 describes one organization with one ownership list and no per-document access model. TBD: whether document-level permissions are needed in V1 is not stated in A2 (owner: A2 team).

### Decisions E

- **Q10.59 Preserving contradictions (mechanism):** The context keeps both items with their source and time, under an explicit "conflict" marker. The system does not silently pick a winner. The agent and critic must consider the conflict, and it is shown to the engineer. TBD: the evidence structure comes from A9.
- **Q10.60 Compressing context:** Order of steps: drop irrelevant and repeated material; reduce long logs to their key lines (errors, counts, time ranges); summarize old conversation turns. Identifiers, numbers, timestamps and error messages are kept word for word. Evidence that is cited is never compressed. Each compressed part keeps a pointer to the full record. Evaluation checks that compression does not lose important facts.
- **Q10.61 Prioritizing evidence (mechanism):** First keep what is mandatory: the task, constraints, the current hypothesis and directly cited evidence. Then score the remaining evidence by relevance to the question, source reliability, recency, and whether it supports or contradicts the hypothesis. Fill the token budget from the top, leaving room for the answer. What is left out is listed with pointers to the full records. TBD: the evidence kinds come from A9.
- **Q10.62 Provenance through summaries:** Every claim in a summary carries the id of the source evidence record (and the span when needed). The summarizer is required to output these ids. A check confirms every claim has at least one valid id, and a summary without them is rejected.
- **Q10.63 Why summaries do not replace evidence:** A summary loses detail and can contain mistakes or invented statements. It is an interpretation, not the original observation. Engineers and audits need the original records to verify it. If only summaries existed, errors could not be found, and summaries of summaries would pile up errors. So both are kept, and the summary points to the records.
- **Q10.64 Reproducing a diagnosis (mechanism):** Preserve: prompt version and skill version; model identity (Q10.23) and parameters; tool definition version; the version of the context assembly rules and the exact assembled context (or the inputs to rebuild it); the retrieval index revision (Q10.52) with the retrieved chunk ids and spans; the evidence records; compression settings; and the time. TBD: the complete version list comes from A9.
- **Q10.57 Deciding what belongs in the context (mechanism):** Thousands of lines cannot all be sent. Steps: (1) select what is relevant to the question and the current hypothesis (time window, related services, error level, retrieval results); (2) filter by the requester's permissions (Q10.56); (3) fill the token budget in priority order (Q10.61); (4) compress the rest (Q10.60), for example repeated log lines become one line with a count; (5) keep a list of what was left out, with pointers, so the agent can ask for more. Every part keeps its source marker. TBD: the evidence kinds and amounts come from A9.
- **Q10.58 Assembling live telemetry with documentation (mechanism):** The two sources differ in nature: telemetry is recent and numeric, documentation is older and written text. The context holds them as separate labeled parts ("current observations" and "reference documents"), each with its source, time and version. Documents are guidance, not proof: their statements are checked against telemetry. A contradiction is shown and not hidden (Q10.59). Telemetry is fetched fresh and marked with its age; documents come from a fixed index revision (Q10.52). TBD: which telemetry exists and how the agent requests it come from A9.
