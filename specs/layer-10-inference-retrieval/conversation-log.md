### Decisions A

- **Q10.1 Model that generates tokens:** A transformer-based, decoder-only, autoregressive LLM generates the tokens. It computes a probability for the next token, selects one, appends it to the input and repeats until a stop token or the max_tokens limit. The exact model and provider are decided in Q10.2 onward and in A2.
- **Q10.2 Model vs provider:** Treat the model (family, version, model ID) and the provider (who hosts and serves it, and its interface) as two separate things. The platform records both as separate fields, with the exact pinned model version, on every request and result. The same model can be served by different providers, and the same provider offers many models. The application uses its own internal model name that maps to the provider's model ID.
- **Q10.3 Delivery approach without GPU operations:** Primary choice: managed (hosted) inference. A provider runs the model on its own GPUs, and the platform calls it through an API and pays per token. The team does not operate GPUs, drivers or serving software. Fallback, only if a hosted API is not suitable (for example, if incident data may not leave our network): rent GPU servers from a provider and run the model-serving software ourselves. This fallback does not meet the "no GPU operations" condition, because the team operates the serving software. CPU-only inference is not considered for V1 because of speed and scale. The trade-offs (less control, data leaves our network, dependence on provider limits and outages) are handled in Q10.6 and Q10.7.
- **Q10.4 Self-hosted inference vs external provider:** With self-hosted inference, the organization runs the GPUs, the serving software, scaling, uptime and security patches itself. In return it gets full control: data stays inside its own network (data residency), it chooses and pins the exact model version, and it is not bound by a provider's rate limits or deprecation schedule. Costs are fixed and GPU-based, so self-hosting pays off only at high, steady volume; at low or uneven volume the GPUs sit idle and cost more. Only open-weight models can be self-hosted, so closed models such as Claude cannot be used, and quality may be lower. Small models for narrow tasks are easier and cheaper to self-host. With an external provider, the provider handles GPUs, scaling and uptime. We pay per token and start fast, but data leaves our network and we depend on the provider's limits, pricing and outages. The choice between the two is made in A2 and in Q10.6 and Q10.7.
- **Q10.5 Evaluating Claude and Tinker:** Claude and Tinker are two different kinds of service, not substitutes for the same job. Claude is an inference service: we send a prompt, the provider runs its closed model on its own GPUs and returns tokens, and we pay per token. Tinker is a training service: we write the training loop locally on a CPU machine, Tinker runs the heavy training on its GPU clusters, and it fine-tunes open-weight models (using LoRA). It also offers sampling, and trained weights can be downloaded and used elsewhere, for example on our own servers. So they must be compared on the same criteria: the job each one does, who runs what, what data leaves our network, cost, limits and lock-in, which models are available, and output quality on the same test set. Plan: Claude stays in production. The Tinker work is a time-boxed experiment: fine-tune one open-weight model on our incident data, serve it, and compare it with Claude on the same test set (Layer 12). A decision is made only from that comparison. Tinker's current features and model list must be checked in its official docs before use.
- **Q10.6 Responsibilities transferred with managed inference:** The provider takes over the running of the serving infrastructure: provisioning servers and GPUs, deploying and updating the model, serving software and its patches, capacity planning and autoscaling, hardware failures, speed optimizations such as batching and caching, monitoring, and keeping the service up under its SLA (service level agreement, the provider's written promise about availability). The team also no longer needs staff to operate GPUs. The team still owns how its own application uses the service, such as the choice of model and checking the outputs.
- **Q10.7 Own GPU cluster at small volume:** At small and steady volume, running our own GPU cluster is not justified by cost. The GPUs sit mostly idle and still cost money, and the team needs people to run them. A managed provider is cheaper and simpler. The decision can be justified only by control requirements, not cost: (1) data may not leave our network because of law or company rules (data residency); (2) a custom or fine-tuned model that no managed provider hosts; (3) strict control of model versions, with no dependence on a provider changing or retiring a model; (4) special latency or network needs, such as running offline or in a closed network; (5) a firm plan for volume to become large and steady soon, so that fixed GPU cost pays off. Even when justified, start smaller than a full cluster: rent one GPU server, or host the custom model with a provider, and grow only when volume requires it.
- **Q10.8 Serving infrastructure for GPU memory and batching optimizations:** A dedicated LLM serving engine is needed, not a plain model script. vLLM is the main candidate: it manages KV cache memory in small pages (PagedAttention) so less GPU memory is wasted, uses continuous batching (a finished request is replaced at once by a new one, so the GPU stays busy), supports prefix caching, and offers an OpenAI-compatible API server. Other candidates are SGLang (actively developed, reported to suit workloads with repeated prefixes), TensorRT-LLM (NVIDIA GPUs only, high speed goal, longer setup) and Hugging Face TGI (reported by secondary sources to be in maintenance mode, so verify before choosing it for new work). The KV cache itself saves computation time but uses GPU memory; it does not save memory. This choice matters only if we self-host (Q10.3 fallback, Q10.4, Q10.7); with managed inference the provider does this work (Q10.6). The engine is chosen by benchmarking on our own traffic, not from published speed claims.
- **Q10.9 Provider vs application responsibilities:** The provider owns running the model: GPUs, serving, scaling, availability and model updates behind its API. The application owns everything that must behave the same whichever provider is used: building requests in our own format, prompts and prompt versions, model and parameter choice, parsing and validating responses, validating and executing tools, retries, timeouts and fallback, token and cost accounting, logging with provenance, data and security decisions, and checking output quality. Rule: provider differences stop at the adapter, so the agent sees one behavior.

### Decisions B

- **Q10.10 One internal model interface:** The application defines one interface: a ModelRequest goes in and a ModelResult comes out. One adapter per provider implements it by converting our request into that provider's format, calling the provider, and converting the response back. The agent talks only to the interface and never to a provider.
- **Q10.11 Isolating provider-specific communication:** All provider-specific code (SDK calls, authentication, request and response formats, error types, provider model IDs) stays inside the adapter. The agent never imports provider code. A configuration maps our internal model name to a provider and its model ID. Switching an existing provider is a configuration change. A new provider needs one new adapter, and the agent stays unchanged. Contract tests check that every adapter behaves the same way.
- **Q10.12 Normalizing response formats:** Every adapter converts provider output into the same internal structure. A tool call becomes: call id, tool name, and arguments as a parsed object (the adapter parses JSON text). Malformed output is flagged in the adapter and not passed on silently. The raw provider response (or a reference to it) is kept for debugging.
- **Q10.13 ModelRequest fields (mechanism):** request id; incident id and task type; internal model name; instructions and messages (context); available tools (name, description, schema); parameters (max output tokens, temperature, stop sequences); required output format or schema; capability needs (tool calling, structured output); timeout and token budget; prompt version. TBD: the exact task types and per-task values come from A9.
- **Q10.14 ModelResult fields:** request id; content blocks (see Q10.15); stop reason; token usage (input, output, and cached tokens if reported); provenance (provider, provider model ID, internal name, pinned version); start time, end time and latency; retry count; error information if any; reference to the raw response. All of it is written to logs so any issue can be traced back.
- **Q10.15 Representing mixed content:** A response is an ordered list of typed blocks: text, tool proposal, and structured content (parsed JSON plus whether it matched the schema). Other types the provider returns, such as a refusal, also get their own type. Order is preserved. The application reads blocks by type and never depends on a provider's own layout.
- **Q10.16 Representing tool proposals (mechanism):** A tool call from the model is a proposal, not an action. A ToolProposal holds: proposal id, request id, tool name, arguments, status (proposed, valid, rejected, executed) and the validation result with a reason. A validator checks that the tool exists and is allowed for this task, that arguments match the tool's schema, and that permissions and limits are respected. Only valid proposals reach the executor. Rejected ones are logged and can be returned to the model. TBD: the tool list and schemas come from A9.
- **Q10.17 Provider refusal:** A refusal is a normal outcome, not a transport error. The adapter maps the provider's refusal signal to our own result status "refused" and carries the provider's message. The gateway does not retry the same request blindly and does not silently switch providers. The workflow or agent decides what happens next, for example rewording the request or escalating to a person. Every refusal is logged with provenance.
- **Q10.18 Token limit vs completion:** Each adapter maps the provider's stop reasons to a small set of our own: completed, length_limit, tool_request, refused, error. Only "completed" is a finished answer. "length_limit" marks the result incomplete and it is not used as final. The caller may retry with a larger output limit or a shorter input, within budget.
- **Q10.19 Disconnected stream:** A streamed response is complete only when it ends with the provider's explicit completion signal and a stop reason. A dropped connection, or a stream that ends without that signal, gives the status "interrupted". Partial text is kept for logs, flagged, and not used as final. Tokens may already be billed, so usage is still recorded. Retry follows the retry policy.
- **Q10.20 Truncated JSON:** Truncated JSON is an incomplete result and is not repaired by guessing. Check the stop reason first: if it is length_limit, retry with a larger output limit or a smaller task. Otherwise retry within the retry limit. After the limits, fail with a clear error. The raw output is logged.
- **Q10.21 Schema violations:** Validation runs in order: normalize the provider response, parse the JSON, then validate against the expected schema (required fields, types, allowed values). Invalid output is never passed to tools or to the next step. On failure, retry a bounded number of times, optionally sending the validation error back to the model. After the limit, fail with an error and log the raw output and the error.
- **Q10.22 Capability incompatibility:** The gateway keeps a capability matrix per model (structured output, tool calling, and so on). Before sending a request it checks the capabilities the task requires. If a model lacks one, the gateway routes to a model that has it. Where explicitly allowed for that skill, it emulates the capability, for example by asking for JSON in the prompt and applying the Q10.21 validation. Otherwise it rejects the combination with a clear error. Emulation is explicit configuration, never silent. TBD: which skills need which capability comes from A9.
- **Q10.23 Reproducibility:** Preserve for every result and investigation: internal model name, provider, provider model ID, the exact pinned version or checkpoint (never an alias such as "latest"), the model identifier the provider returned in its response, request parameters (temperature, max tokens and so on), prompt version, skill version, tool definition version, and request date and time. If a provider retires a version, exact re-running may be impossible. Then the stored inputs and outputs are the record.
- **Q10.24 Provider comparison:** Compare providers on: model quality for our tasks (from evaluation results), capabilities (tool calling, structured output, streaming, context window, maximum output, caching), limits (rate limits, concurrency), price per input and output token, latency, reliability and SLA, version pinning and deprecation policy, data handling (retention, training on our data, region), and security and compliance. Results go into the provider capability matrix. TBD: the constraints that weight these dimensions come from A2.

### Decisions C

- **Q10.25 Unit of consumption:** The platform measures consumption in tokens, always as two separate numbers: input tokens and output tokens. Each model and provider has its own tokenizer, so the same text gives different counts. Billing follows the provider's own usage report. Our estimates use the tokenizer or token-counting method of the specific model, not a tokenizer of our own design.
- **Q10.26 Distinguishing usage:** Every result records input tokens, output tokens, and cached tokens if the provider reports them, never one combined total, because they are priced differently. Cost per request is input tokens times the input price plus output tokens times the output price, taken from a price table per model.
- **Q10.27 Estimating and controlling spend (mechanism):** Every call has a maximum output limit. Before a call, the worst-case cost is estimated from the counted input and that limit. Each incident has a total budget that covers all its calls, and calls stop when it is used up. A price table per model is kept. Test runs on each candidate model, including expensive ones, give the real token counts per task type, and from these an expected cost range per task type is set. Actual and estimated cost are recorded for each call, and an alert is raised when a call or incident goes outside its range. TBD: the cost limits come from A2.
- **Q10.28 Per-incident budget (mechanism):** Each incident has one total cost cap (value from A2, Q2.16 and Q2.18). A budget ledger per incident holds the limit, the amount spent, and the amount reserved. Every call draws from it through a reservation (Q10.29). When the remaining budget cannot cover the next call, the call is refused, and the investigation ends with the best result so far or escalates to a person. A per-call output limit is a separate, smaller guard. A separate emergency reserve pool exists outside the incident budgets and is used only in emergencies. Which cases qualify, and who approves, is decided together with the stakeholders. TBD: all amounts come from A2.
- **Q10.29 Cost reservations:** Before a call starts, estimate its worst-case cost (counted input tokens plus the maximum output tokens, priced) and reserve that amount from the incident budget in one atomic step. If the budget cannot cover it, the call waits or is refused and does not start. When the call finishes, replace the reservation with the real usage and release the unused remainder. Because the reservation happens before the call and cannot be taken twice, several parallel calls cannot together exceed the budget.
- **Q10.35 Missing usage report:** Never record zero usage. Record an estimate, flagged "estimated": input tokens counted by us, output tokens counted from the text received, or the maximum output limit if the response was lost. The estimate stays charged to the budget. The platform keeps its own usage log and regularly reconciles it with the provider's usage reports and invoices. Differences correct the ledger and improve the estimates.
- **Q10.36 Why not release the reservation at once:** The tokens are already consumed and billed, but their amount is unknown. Releasing the reservation would show that money as free while it is actually spent. New requests could then use it, and the total spending would go over the cap. So the reservation is kept (at the worst case) until the real usage is known, or until an estimate replaces it, flagged as uncertain.

### Decisions D

- **Q10.40 Runbooks during investigation (mechanism):** Runbooks are ingested into the same searchable index as other documents (Q10.42). The agent gets a retrieval tool it can call during an investigation with a query, for example an error code or service name. It receives the most relevant runbook sections with their source, version and section path. Runbooks are reference information for the agent, not commands: any action they suggest still goes through the normal tool validation (Q10.16). Incident priority or service name can be stored as metadata to filter results. TBD: which runbook sources exist comes from A2.
- **Q10.41 Retrieval improving answers:** Without retrieval the model answers only from what it learned in training, which knows nothing about our systems and may be out of date, so it may guess. With retrieval, at the time a question is asked, the platform searches our documents, puts the most relevant passages into the prompt, and the model answers from them. This lets answers use our own current procedures, cite the source passage, and be checked more easily. Retrieval happens when a question is asked, not during ingestion. Ingestion is the earlier preparation step (Q10.42).
- **Q10.42 Ingestion process:** (1) Collect documents from the agreed sources. (2) Read and clean the text while keeping structure (headings, code blocks). (3) Split into chunks with heading-aware chunking (Q10.43, Q10.44). (4) Attach metadata to each chunk: source, document id, version, heading path, date. (5) Build the search index (BM25 first) as a new index revision, so the previous revision stays usable. (6) Check the result with counts and sample searches. (7) Re-run when documents change, including removing deleted ones. Index revisions, stale documents and deleted documents are covered in Q10.52 to Q10.55.
- **Q10.43 Dividing documents into retrievable units:** Split each document at its natural structure (sections and subsections), so every chunk covers one topic and can be understood alone. Chunks have a size limit; a section that is too long is split further at paragraph or step boundaries, with a small overlap. Very short neighbouring sections may be merged. Each chunk keeps a pointer to its document and position.
- **Q10.44 Heading-aware chunking:** Chunks are cut at headings, and the full heading path (for example "PostgreSQL > Failover > Step 3") is stored with every chunk, both in the indexed text and in the metadata. A fixed-size cut can separate "run promote" from the heading that says which system and situation it belongs to; heading-aware chunking prevents this. Code blocks and numbered steps are never cut in the middle.
- **Q10.45 Lexical retrieval for exact identifiers:** Use BM25, a lexical (exact word match) method. Engineers search for exact strings such as error codes, function names and configuration keys, and embedding-based search can blur such strings with similar ones. The tokenizer must keep identifiers such as ERR_4012 or max_connections whole (or index them both whole and split) so exact searches match.
- **Q10.46 Importance of rare terms:** BM25 weights each term by inverse document frequency (IDF): a term found in few documents gets a high weight, and a term found in almost all documents (such as "error") gets a low weight. So a rare error identifier that appears in only a few documents ranks those documents high. BM25 also limits the gain from repeating a term many times and adjusts for document length.
- **Q10.47 Vector embeddings:** Embeddings turn text into vectors by meaning, so a question and a document that use different words with similar meaning end up close together. The question is embedded and compared with the chunk vectors (cosine similarity), and the closest chunks are returned. This fixes vocabulary mismatch, for example "the database answers slowly" against "high query latency". Weaknesses: similar exact identifiers can blur, and it needs an embedding model and a vector index, which is extra infrastructure.
- **Q10.48 Search by conceptual similarity:** Semantic (vector) search: chunks are embedded at ingestion and stored in a vector index. At search time the query is embedded and the nearest chunks are returned.
- **Q10.49 Combining keyword and semantic results:** Hybrid retrieval: run BM25 and vector search separately, then merge the two ranked lists with Reciprocal Rank Fusion. Each document gets about 1 divided by (60 plus its rank) from each list, and the scores are added. Documents ranked high in both lists rise to the top. RRF uses ranks and not raw scores because BM25 scores and similarity scores are on different scales.
- **Q10.50 Why BM25 first:** Exact technical identifiers are the main need, and BM25 handles them reliably and explainably. It needs no embedding model, no vector database and no extra cost, runs inside the program, and gives the same output for the same input, so it is reproducible. Embeddings are added only if evaluation (Q10.51) shows that vocabulary mismatch causes missed documents.
- **Q10.51 Measuring retrieval quality:** Build a labeled set of real questions with known correct documents or chunks (ground truth). Measure Recall@10 (is the correct document in the top 10), Precision@10 (how many of the top 10 are relevant) and MRR (mean of 1 divided by the rank of the first correct result). Re-run the same set after every change to chunking or search method and compare. Keep the results together with the index revision.
- **Q10.52 Immutable index revisions:** Every ingestion run creates a new index revision with its own id, and a revision is never edited. It records the documents, their versions and content hashes, and the chunking and tokenizer settings. Each investigation records the revision it used, so it can be reproduced later. Old revisions are kept for the agreed retention period, or can be rebuilt from the stored document versions.
- **Q10.53 Preserving source version and text span:** Each citation stores the document id, the document version, the exact text span (start and end position) and a content hash of the cited text. If the document changes later, the cited text can still be shown from the stored version, and the hash proves it was not altered.
